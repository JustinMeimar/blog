Pruning through a codebase like SpiderMonkey you will find copious type
aliases. For instance [`typedef uint8_t jsbytecode`][1]. Or [`typedef
unsigned char Latin1Char`][2]. Intuitively this is good software
architecture, but perhaps the reason is a bit subtle, since aliases are
purely syntactic. I was recently forced to articulate precisely why so that
my little friend Claude would stop spewing raw `int`s all over my
implementations. Here is what I told Claude:

> Mature C++ projects start to read like a custom dialects/DSL through the use of well-named type
> aliases. For instance, Clang will [alias an unsigned integer to `BlockID`][3].
> While these are [purely syntactic substitutions][4], they are useful for
> reading and writing code.
>
> Well named type alises increase signal when reading code. 
> It is immediately clear what `BlockID i=0`
> refers to, where as for `unsigned i=0` I may guess as an index (from a large prior
> of seeing index loops), but I will not know the full context. Type aliases may 
> also shorten nested compound types; `std::vector<std::tuple<int,int>>` is more
> noisy to read than `MyVector<Coordinate>`.
>
> Type aliases also have utility beyond lowering the perplexity for readers.
  They establish a prudent
> refactoring boundary. What happens if, one day, we need to add some more
> semantics to `BlockID`? Suppose we need to elevate it's function into a
  `struct`. We
> can use refactoring tools to find and change every occurrence of
> `BlockID` in our project. If it is merely an unsigned integer, we will hit the
> super-set of all `unsigned` types in our program. Not good.
