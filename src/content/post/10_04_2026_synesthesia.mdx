## Typed Completions

Sometimes you need the output of an LLM to adhere to a particular structure.
For this reason OpenAI, among other providers, offer [_Typed
Completions_](). Behind the scenes, the model is informed of some structure
an object the generation is meant to be a valid instantiation of. Most
likely the system prompt is amended to instruct: "produce JSON of this
structure", which is then parsed and returned to the user. If it fails
to parse an error is returned to the user. In essence it is a turning a
generative model output into a `Maybe<T>` monad.


```python
character = {
    "hair": str
    "personality": str,
    "age": int
}
res = llm.generate("My favourite Byronic Hero", type=character)
if not res.error:   # may fail to produce a character 
 print(res.output)  # here is guaranteed to be syntactically correct
```

_Typed Completions_ were intriguing to me right from their inception around
2023 since they bekoned towards some heterogenous use of generative and
classical software: of imperative, deterministic, and otherwise "regular"
software along side unreliable, potentially slop producing, but also
sometimes creative and flexible generative models.

## The Preimse: Using Pydantic to be Pedantic

What is most convenient about _Typed Completions_ is that they can be
derived from any Python object which inherits from the [`pydantic`]()
package's `BaseModel` class. These classes can be composed, allowing for the
generation of nested structures. Any primitive type, like `string` or `int`,
is type-checked by the API, along with user types which de-sugar (this is imprecise) into
primitive types, like a `StrEnum`.

```python
from pydantic import BaseModel

class Ability(Enum):
    Fly,
    Clone,
    Explode,

@dataclass
class Character(BaseModel):
    name: str
    backstory: str
    abilities: List[Ability]
   
    @classmethod
    def generate(cls, *args):
        return self.model.complete(prompt=f"""
            Create a character for a fantasy game from this users description: {}.
            The name must comprise a first and last name. A character must have
            no more than two abilities, and can not simeltaneously fly and explode.
        """.format(*args), type=cls)

    def validate(self):
        assert len(self.name.split(' ')) == 2 # first and last
        assert len(self.abilities) <= 2 # not more than two
        assert not ("Explode" in  self.abilities and \
                    "Fly" in self.abilities)

c1 = Character("A Villain from a Volcano") # will likely select explode...
c2 = Character("Someone like Princess Peach.")
```

The example above shows a character creation pipeline. The generation for
each class is fed itself as the type parameter, then uses a generation
prompt, parameterized by some user specification, to seed the values.
Essentially an instance of a class can be created with it's fields values
being _generated_ rather than _assigned_. Because each class retains regular
Python semantics, a _validation_ method can be automatically invoked after
each generation to assert more stringent properties beyond syntactically
valid JSON.

Contemplating what more elaborate hierarchical structures look like, it is
clear that we are building large, acyclic graphs (Trees) via composition of
Python objects which can be "generated". We will need some algorithm for
traversing this graph and invoking the generations. Here is where it gets
tricky. In what order to generate the graph? From a strict computer science
approach, we should generate a node any time it's producer nodes are ready.
But the semantics (should I dare use that word) of this synthesis are more
sensitive. Consider the case of a book.
