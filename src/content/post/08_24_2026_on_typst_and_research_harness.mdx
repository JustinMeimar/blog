This post describes the research setup I used while writing my first paper,
which will be submitted to [CGO 2027](https://2027.cgo.org/). Whether it
gets accepted or not, the process of writing a paper has become immensely
interesting to me. It is my impression that one's particular methodology for
research—i.e., the _system_ or _strategy_ one uses to complete their
research—is mostly a hidden art. Common wisdom floats around, such as
Simon Peyton Jones's advice to "[write the paper
first](https://www.microsoft.com/en-us/research/academic-program/write-great-research-paper/),"
but the general _end-to-end_ system people use to complete their research
seems under-discussed.

### Magic Number Bad

Let me first introduce a problem that you may have encountered if you write
papers. You are writing a section and insert some numerical result from an
experiment. If you are editing in
[LaTeX](https://www.latex-project.org/), that might look like this:

```latex
\section{Results}

Silencing \textit{BRCA1} cut DNA repair efficiency by 60\%
compared to controls ($n=12$).
```

In doing so, you have just introduced two dependencies that you must
manually keep track of. If you rerun the experiment, the `n = 12` value may
change. If the baseline for comparison is reconsidered, the 60% figure may
change. Moreover, if these results are repeated—for example, in the abstract
and evaluation sections—you have now duplicated the source of
truth. In computer science terminology, if we consider the paper as a
program, we might say this example uses [magic
numbers](https://refactoring.com/catalog/replaceMagicNumberWithSymbolicConstant.html)
where it should use variables.

Now, perhaps the iteration rate over experimental setups is lower in other
fields than it is in computer science, where the virtualization of resources
can create a degenerative abundance of choice and a lack of decisiveness.
Other sciences still have to interface with the physical world, and
everything in the physical world is more expensive. In any case, I suspect
there are still a large number of representational decisions made long after
experiments are run for which this churn in numerical results occurs.

This leads to the first principle of research: no magic numbers. [In
Typst](https://typst.app/docs/tutorial/making-a-template/), I can create a
variable, assign the value once, and reference it any number of times in the
prose.

```typst
#let repair_reduction = 60
#let sample_size = 12

= Results

Silencing _BRCA1_ cut DNA repair efficiency by #repair_reduction% compared to controls ($n=#sample_size$).
```

### The Distinct Responsibilities of Scripts

Despite rolling around in an abundance of virtual resources, performing
experiments on a computer shares at least one characteristic with the hard
sciences: waiting around for results. It is desirable that, once these
long-running experiments have been performed, they not be run again
unnecessarily. Ensuring this is the case comes down to the organization of
scripts.

Suppose we want to infer the behavior of a black-box random generator. On
each iteration, it emits a letter from `A-Z` according to some hidden
probability distribution. Collecting one billion observations takes a long
time, so we would rather not repeat the experiment unnecessarily. Our goal is
to estimate the hidden distribution from those observations. Consider two
configurations:

_Configuration A_: A single script, `do_research.py`, runs the generator,
counts the occurrences of each letter, and holds those counts in memory in a
map like `letters = {"A": 123, "B": 544, ..., "Z": 5541}`. It then hands the
counts to a routine that performs [maximum a posteriori (MAP)
estimation](https://en.wikipedia.org/wiki/Maximum_a_posteriori_estimation),
fitting a distribution from some family to the observations. Finally, it
plots the estimate using [Matplotlib](https://matplotlib.org/stable/) and
saves the figure to a PDF. None of the intermediate results survive after the
script exits.

_Configuration B_: Three scripts called `experiment.py`, `analyze.py`, and
`derive.py`. The experiment script runs the generator and records its raw
observations in a uniquely named artifact such as
`observations_2026-08-24_15-32.jsonl`. The analysis script reads that artifact,
counts the letters, fits the model, and writes its estimate to
`analysis_2026-08-24_15-38.json`. Finally, `derive.py` consumes the analysis
artifact, saves `distribution_2026-08-24_15-38.pdf`, and opens the figure.

By designing scripts with _orthogonal_ and _composable_ responsibilities, the
research pipeline can be paused or resumed from any stage. If there is a bug
somewhere in the analysis or derivation, the experimental results can likely
be salvaged.

Designing scripts with these three orthogonal responsibilities also allows
for _horizontal scalability_. If you want to compare two statistical
methods, say MAP and [maximum likelihood estimation
(MLE)](https://en.wikipedia.org/wiki/Maximum_likelihood_estimation), you can write two
analysis scripts, point them both at the same observations, and design a
derivation script that consumes both outputs and compares their fit on
held-out data. If you want to iterate on figure designs, the derivation
scripts scale similarly.

Lastly, the experiment layer can scale by adding variants. Suppose we want to
run the pipeline against two black-box generators with different hidden
distributions. We can produce `experiment_A.py` and `experiment_B.py`, then
connect their results to the same analysis and derivation scripts by way of a
shared JSON output format that acts as a contract.

> This entire process should be reminiscent of those spinny cylinder things
  in kids' parks or in IKEA, where you can create a different creature by
  spinning the head, upper-body, and lower-body cylinders into unique
  configurations.

### Kind of Like Burying Fossils

Some sort of split like the one described above is likely not too uncommon.
What I'll describe in this section is a research harness that presents the
interfaces for automatically composing a research pipeline from these kinds
of scripts. The project is called
[Fossil](https://github.com/JustinMeimar/fossil), because running an
experiment should be somewhat like burying a record in the sand. It should
come up one day when you dig for it, untouched and with certain provenance.
Never should you encounter an experimental result and ask yourself: "When,
where, or how was this created?"

Examples probably work better than words. My experiments are laid out in a
directory like so. Each experiment is prefixed with the section and subsection
it renders into.

```shell
➜  ls -l
Aug 17 10:07 0-0-static-tables
Aug 20 19:58 3-3-inter-workload
Aug 22 17:02 3-4-sm-v8-ics-micro-bench
Aug 17 16:07 6-1-corpus-construction
Aug 17 10:08 7-1-corpus-coverage
Aug 24 10:32 7-2-ambermonkey-perf
Aug 23 10:15 7-3-v8-jitless-comparison
Aug 17 10:24 7-4-indirection-overhead
Aug 23 10:15 7-5-cross-process-memory-sharing
Aug 17 10:08 7-6-binary-size
Aug 17 16:54 7-8-aot-attachment-cost
Aug 20 14:02 configurations.toml
Aug 23 10:14 project.toml
Aug 23 10:15 README.md
```

Each experiment directory contains a [TOML](https://toml.io/en/)
configuration. Here is the configuration for `7-2-ambermonkey-perf`, which
measures [Speedometer 3](https://browserbench.org/Speedometer3.0/about.html).

```toml
name = "7-2-ambermonkey-perf"
description = "Speedometer 3 AmberMonkey performance evaluation"
default_iterations = 3
allow_failure = false

[analyze]
speedometer-detail = "analyses/parse_speedometer.py"

[figures.subtest-bars]
analysis = "speedometer-detail"
script   = "figures/subtest_bars.py"

[figures.tier-throughput]
analysis = "speedometer-detail"
script   = "figures/tier_throughput.py"

[figures.aot-tradeoff]
analysis = "speedometer-detail"
script   = "figures/aot_tradeoff.py"

[tables.perf]
analysis = "speedometer-detail"
script   = "figures/speedometer_table.py"

[variables]
MACH    = "./mach raptor -t speedometer3 --app firefox --browser-cycles 1 --page-cycles 3 --binary @BIN_AOT --setenv MOZ_HEADLESS=1"
ION_OFF = "--setpref javascript.options.ion=false"
RESULT  = "cat testing/mozharness/build/raptor.json"

INTERP   = "JIT_OPTION_disableJitBackend=true"
AOT      = "JIT_OPTION_useAOTImage=true JIT_OPTION_aotOnly=true"
IC_ONLY  = "JIT_OPTION_aotSkipBaselineFn=true"
NO_REGEX = "JIT_OPTION_nativeRegExp=false"

[variants]
interp-only    = "@CLEAN_AOT $INTERP                    $MACH          1>&2 && $RESULT"
aot-corpus-ic  = "@CLEAN_AOT $AOT    $IC_ONLY $NO_REGEX $MACH $ION_OFF 1>&2 && $RESULT"
aot-corpus     = "@CLEAN_AOT $AOT             $NO_REGEX $MACH $ION_OFF 1>&2 && $RESULT"
default-no-ion = "@CLEAN_AOT                            $MACH $ION_OFF 1>&2 && $RESULT"
default        = "@CLEAN_AOT                            $MACH          1>&2 && $RESULT"
```

The top-level fields name the experiment and set its iteration and failure
policy. `[analyze]` associates an analysis name with a parser, while each
`[figures.*]` and `[tables.*]` entry connects that analysis to a derivation
script. `[variables]` factors out shared command fragments, and `[variants]`
composes those fragments into the five configurations that Fossil runs and
records.

### Wiring the Harness into Typst

The first section established that raw numbers in prose should be
canonicalized to a single variable. The second section emphasized that a
giant bag of scripts should be partitioned into the tuple `(Experiment,
Analysis, Derivation)`. The third section yapped about my custom research
harness, which uses this process.

This section motivates how a research harness can be configured to write
experimental outputs _directly into the variables a Typst program consumes_.
Doing so allows one to rerun an experiment, regenerate its derived data, and
have the manuscript update automatically on its next compilation.

In Fossil, the project configuration points `paper_dir` at the manuscript's
JSON directory:

```toml
paper_dir = "/home/justin/spidermonkey/ambermonkey/paper/lib/json"
```

The `[tables.perf]` entry above connects the `speedometer-detail` analysis to
the `speedometer_table.py` derivation script. Running the table command
reruns that analysis, pipes its structured output into the derivation script,
and writes the resulting JSON into `paper_dir`:

```shell
fossil table 7-2-ambermonkey-perf --table perf
```

Typst can [read that JSON
directly](https://typst.app/docs/reference/data-loading/json/). In my paper, a
small accessor in `lib/tables.typ` turns a filename and key into a value:

```typst
#let json-field(name, key) = {
  let data = json("json/" + name)
  assert(key in data, message: name + ": no field " + key)
  data.at(key)
}
```

`constants.typ` then uses formatting helpers to give paper-facing names to
particular experimental results:

```typst
#let sp3-aot-speedup = pct(
  json-field(
    "restricted-execution-perf.json",
    "aot_over_interp_speedup",
  )
)
```

The manuscript imports those constants once and uses them as ordinary Typst
variables:

```typst
#import "constants.typ": *

AmberMonkey improves Speedometer 3.1 throughput by #sp3-aot-speedup over
bytecode-only execution.
```

No numerical result is copied into the prose. The experiment record feeds
the analysis, the analysis feeds the derivation, the derivation feeds the
Typst variable, and the variable feeds every occurrence of the result in the
paper.
