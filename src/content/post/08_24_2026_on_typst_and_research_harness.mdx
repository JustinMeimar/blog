> TLDR: How to comb a hairball of research scripts into a neat, organized
  harness. Specifically, one which auto-updates your paper's metrics when
  experiments run. We also reflect on designing software that can
  _scale horizontally_ with AI agents that have a propensity to spew
  code like a broken fire hydrant. 


A research harness organizes the measurement of software. This includes
running experiments, analyzing data, and generating figures. Papers hardly
arises from a linear sequence of keystrokes. An ergonomic harness aims to
reduce the friction of the continuous iteration, backtracking and pivoting
involved in research.

A project may span months, or even years -- a duration long enough to
justify migrating from a collection of ragged scripts to a well-thought-out
tool. Experiments will change, analyses will be adjusted, and figures will
be swapped. A harness should make all these changes well defined. It should,
by construction, enforce experiments to be reproducible, versioned, and
produce artifacts with clear provenance.

The alternative is... well you may have experienced it already. A result,
even if it's excellent, is junk if it's provenence has been lost. The goal
is to avoid ever asking: "Where did this result come from?", "How did I run
this experiment last time?", or, the worst of them all, "Which of these
results is the right one?".

With this deplorable circumstance in mind, we are motivated to view the
entire research process from an software design lens. The harness described
in this post is distilled from experiences writing my first paper this
summer, and possibly finding myself in the situations mentioned above.

### The Paper _is_ the Program 

> Throughout this post I use [Typst](https://typst.app/docs/), a dual
  type-setting and scripting language. The syntax should be intuitive.

In programming, an old adage goes on about "not repeating oneself."
Duplicate sources of truth ripen the area for programmer induced errors.
Yet, when writing a paper, there is a natural impulse to write the prose
exactly how it is expected to appear. Consider a headline result from an
abstract, which almost certainly is repeated again in some later section.

```typst
=== Results
The change cut DNA repair efficiency by 60% compared to controls (n=12).

// The middle of your paper ....

=== Evaluation
A normalized experiment using a sample population of 12 resulting in
the DNA repair efficiency improving by 60% over the controlled population.
```

Ignoring whether this biology jargon is coherent, the issue of duplicated
metrics is clear. After re-running an experiment, every occurrence of `60%`
must be updated manually. If the experimental design changes, same goes for
`n=12`. Without abstracting repeated metrics into variables, one must
vigilantly update every occurrence independently. Even if you (or more
likely your terminally online robot friend) are shrewd enough keep every
metric updated, it is manual work nonetheless. Why not automate it?

Keeping experimental parameters in _variables_ is an admittedly quite basic,
but necessary step towards our goal of a well-oiled research harness. On
it's own, this is merely the
[DRY](https://en.wikipedia.org/wiki/Don%27t_repeat_yourself) principle.
Simple as it may be, variables will become the interface from which the
harness delivers experimental updates automatically. That leaves us with the
first princple: _No magic numbers in Prose_.

```typst
#let repair-efficiency = "60%"
#let sample-size = 12

=== Results
The change cut DNA repair efficiency by #repair-efficiency compared to controls (n=#sample-size).

=== Evaluation
A normalized experiment using a sample population of #sample-size resulting in
the DNA repair efficiency improving by #repair-efficiency over the controlled population.
```

### A Common IR for Experimental Results 

Some may say assigning variables once, within the draft, is good enough.
But as a true programmer, I am lazy. Notice that the research harness
continually observes the latest results. Why not inform the harness of our
draft, having _it_ update the paper? Herein lies the utility of _Typst as a
programming language_. The harness will be setup to write the artifacts from
an experiment, while Typst project reads them in. JSON tables will
effectively become an intermediate representation. As an invariant,
experiments will emit their results in a table structure. Some Typst
functions will allow reading arbitrary rows, fields and columns from said
structure. To illustrate, suppose the harness emits tables shaped like so:


```json
{
  "table": "Speedups over the Baseline",
  "columns": ["Baseline", "Version-A", "Version-B"],
  "rows": {
    "Workload A": { "Baseline": 1, "Version-A": 1.4, "Version-B": 1.8 },
    "Workload B": { "Baseline": 1, "Version-A": 0.9, "Version-B": 1.5 },
    "GeoMean":    { "Baseline": 1, "Version-A": 1.12, "Version-B": 1.64 }
  }
}
```

The rows and cells have names, so we can look up a result without knowing
its position. Adding another workload or version leaves existing lookups
intact. The `columns` list gives the order in which to display the values.
We can write a small Typst library to render the table or retrieve a value.
Typst already provides `json()` to read the file; the helpers just operate
on the loaded data.

```typst
#let render-json-table(data) = {
  let cells = data.rows.pairs().map(((name, row)) => (
    name, ..data.columns.map(column => row.at(column))
  )).flatten()

  table(
    columns: data.columns.len() + 1,
    table.header([Workload], ..data.columns),
    ..cells,
  )
}

#let cell-value(table, key) = table.at(key)
```

The accessor is deliberately just a name for Typst's dictionary lookup.
For this software benchmark, we can now derive the table and the headline
result from the same file:

```typst
#let results = json("results/speedups.json")
#let geomean = results.rows.at("GeoMean")
#let version-b-speedup = cell-value(geomean, "Version-B")

#render-json-table(results)

=== Results
Version B achieves a geometric mean speedup of #version-b-speedup×
over the baseline.
```

JSON tables of this form impose a constraint on how our harness emits
results. Of course, for forms which escape the rigidity of a table,
arbitrary figures can be generated. But otherwise, this JSON table will
become the representation mediating our draft and harness. If we are using a
command like `typst watch`, which incrementally re-compiles our paper live,
we can even observe our draft update in real time once an experiment
completes. Pretty cool!

### Fossil -- The Research Harness

We can now divert to the design of the harness itself: Fossil. The name is
meant to evoke the imagery of uncovering a long buried fossil. In our case,
it is likely a research artifact from many months ago.

To elaborate on the analogy, suppose this fossil was buried in pristine
condition. It follows we can confidently dig it up and reason about it. On
the other hand, if it was buried in some catastrophe, then upon digging it
up we find ourselves at a loss for what exactly we are looking at.

This forms our previously mentioned "deplorable" research circumstance.
Finding a seemingly great result, only it exists inside an ambigiously named
`results.json` file. What species it this `results.json` creature? Is it
even a organism at all, or merely some funnily shaped petrified wood? With a
research harness, we should be _certain_ this fossil was buried at. This
leads to the second principle: _all artifacts have clear provenance._

### Distinct Roles of Scripts

The heart of fossil is three distinct script roles: running experiments,
analyzing outputs, and producing structured artifact. Orthogonal-izing
these roles allows the research project to scale much more effectively.

First, a runner invokes the program under study, collects its outputs, the
state of the machine, exit status, and anything else that is irrespective of
the contents of the output. A run produces a record: an unstructured file
comprising the runs output and meta-data. 

The second class is an analysis script. An analyzer takes the verbose,
unstructured outputs of a run and produces a neat JSON file. Sometimes it
will emit the typst-readable JSON table immediately, other times it will be
more bespoke. The analysis is trivially repeatable. A pure function over a
record, producing the same results each time. Separating a run from a record
allows a many-to-many relation between records (perahps three records run
under different experimental conditions) and analyses (suppose wall-clock time,
and output score).

The third class is for artifact scripts. These produce either PDF figures
for the paper, or JSON tables to be referenced indirectly. Like the run and
analysis separation, decoupling the artifact script allows various
presentations of the same data. I have often pointed an agent at some
analysis output and asked it to "create several interesting plots which tell
the story of this data". Another benefit of decoupling, of course, is when
the run and analysis are expensive. There is no reason for a plotting script
to wait around for an anlaysis to re-compute.

The roles each build on-top of the previous. Other than that, Fossil merely
provides indirection for invoking scripts through common cli commands:
`fossil run`, `fossil analyze` and `fossil artifact`. By combing otherwise
ragged scripts through a unified interface, we avoid a hairball of
unorganized scripts. This outcome is particularly accessible outcome given
the willingness of AI agents to spay code everywhere. If agents are writing
scripts, at least the complexity is confined to its role.


This scratches at what I think is a design principle for programs that are
heavily used by agents. Structured boundaries allow agent written code can
proliferate en-mass, but in an organized, horizontally scalable fashion. No
matter how crazy the agent gets, a script is constrained to assume do one
particular job, and do it well.

### Variants

Variants are the last key aspect of the harness. They define distinct
configuration in which a runner script will be called. For example, variants
for a compiler benchmarking experiment may be: `{-O1, -O2, -O3}`, describing
three different optimization levels. A record produced by a run is tagged
with it's variant. There is not much more too it. Variants are a simple
and essential aspect of a harness.

### The Fossil API

Most of the implementation details can be found in the [Git
repository](https://github.com/JustinMeimar/fossil). A research project
recieves it's own `project.toml`. Experiments live in adjacent directories,
each containing their own `fossil.toml` where experiment variants, runner
scripts, analysis scripts and artifact scripts live. I typically prefix my
experiments with the section of the paper their results are emitted into.

```
Aug 17 10:07 0-0-static-tables
Aug 20 19:58 3-3-inter-workload
Aug 24 10:32 7-2-ambermonkey-perf
Aug 17 10:24 7-4-indirection-overhead
Aug 23 10:15 7-5-cross-process-memory-sharing
Aug 17 10:08 7-6-binary-size
Aug 23 10:14 project.toml
```

A per-experiment `fossil.toml` looks like so:

```
name = "0-1-baseline-cache-simulation"
default_iterations = 1
allow_failure = true

[variants]
speedometer3 = "record.py"
jetstream3 = "record.py"
tp6 = "record.py"
manual = "record.py"

[analyze]
recurrence = "analyze.py"
detail = "analyze_detail.py"

[artifacts.detail]
script = "analyze_detail.py"
format = "json"
```

Experiments can be invoked from the CLI via `fossil bury <experiment> --variants <variants>`. I've also played around with a TUI and a web-view from which records
can be viewed, experiments can be kicked off, and figures can be generated.

### Leaving it to You Now

I've focused on the principle aspects of a research harness, and remained
deliberately skimpy on the details of `fossil` for a reason. Building a
harness is fun and relatively cheap with agents. Additionally, a harness
should be custom-tailored. The age of single user software is here, and it
is a great time. I hope this post has inspired the design of your ownc
custom research harness!
