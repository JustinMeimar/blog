> The execution of dynamically typed languages can approach native speeds
  using JIT compilation, but at what cost?

Constraints make problem-solving interesting. _Luamura_ is fork of the [PCU
Lua 5.5]() interpreter that aims to improve execution performance while
restricting itself in two, possibly debilitating ways.

First, no dynamically allocated/marked executable memory, i.e _no JIT_. For
a dynamically typed language, this is the equivalent of tying our hands
behind our back. Why impose such a brutal constraint? Depending on dynamic
executable memory limits the deployment options of an executable. Targeting
the [WASM]() platform, for instance, dictates that all executable memory be
statically allocated. Additionally, JITs have a warmup phase. In long
running applications warmup is ammortized once the JIT reaches a
stead-state. But in short-lived applications, such as [Function-as-a-Service
(Faas)](), the applications run-time may be shorter than the warmup itself
[^1]. Hence Luamura is an AOT compiler.

Second, no duplication of Lua bytecode semantics. Duplicating sources of
truth is fundamental principle in programming, yet JIT compilers often
eschew it for pragmatic reasons. The basic execution tier, the interpreter,
implements the generic semantics of each bytecode in the language. JIT code
seeks to provide guarded, specialized execution of the guest program,
effectively cutting corners around the slow, generic routines. JIT code
commonly will:[promoting stack values to registers](), skipping unboxing
routines, emitting type-specialized code, etc. Emitting native code at
run-time requires some assembly templates, usually wrapped around a
[macro-assembler](). If a JIT has multiple tiers, it may duplicate operator
semantics in each. At once point, V8 juggled nine different (tier,backend)
pairs. The authors of Luamura are scared by the subtle and stringent
intracacies of bytecode semantics. Hence luamura uses the [First Futamura
Projection] to derive a compiler from an interpreter.

As we will see, what qualifies as the First Futamura Projection is
effectively a type-generic [Baseline Compilation]. Perhaps slightly weaker
in that Baseline compilers typically do stack-to-register promotion through
a single-pass abstract interpretation. Luamura erases the interpreter
dispatch overhead, and that's it. Here in part one, looking at a +500 loc
diff (with LLVM as a dependency), that is not a bad place to start. However,
there are many more potential elaborations.

## Reifying the Nebulous Futamura Projection

The basic idea is as follows. Write a small main functon to accept a lua
module, and link against `liblua` to access the entire run-time library
through the C-ABI. Parse each lua function into bytecode and lift it into a
[CFG](). By handing the CFG to our code-generator, the LLVM IR builder can
etch out the basic blocks and control flow structure given by the guest
bytecode.

The complication arises when we consider lowering a basic block of lua
bytecode. An interpreter would chew through each bytecode perfectly, but it
incurs some dispatch overhead between each op. This is what we seek to
avoid. 

The ad-hoc solution Luamura uses is to make each op-handler a visible
function [^2]. When lowering a CFG block contained with bytecode, we can
emit an LLVM call instruction to the respective op-handler annotated with
["must-inline"](). The entire, generic function body then gets inlined into
the basic block, with no branching in-between.

There are a few obvious implications of such a technique. First, a explosion
in code size can be expected. Comparing a compiled function to it's
interpreter counterpart, the former effectively un-factors the de-duplicated
work of the later. Abstracting duplicated work into a single function is the
natural instinct of any programmer, but for binaries it can be effective to
do the opposite. Consulting the interpreters dispatch loop to find the right
op-code handler is, in a world with infinite code-caches, an unnecessary
indirection. And indirection is overhead.


The second implication is that a proliferation of run-time calls still
exists. We inline an op-handler to one-degree. Any calls in the handler are
not recursively inlined, so exist in the native function body.

## Areas for Improvement

- Promoting Boxed Lua Values from the VM stack into registers in native
  code.

- A formulation of type-specialized fast-paths which reuses op-handlers.

## Conclusion

Luamura achieves some marginal gains while adhering to our two constraints:
no dynamic executable memory, and reuse of interpreter semantics. ~500 LOC
is a good starting point, but future improvements will require an SSA
intermediate representation, some more co-design with the interpreter, and a
bunch of analysis passes to prove what VM state is safe to specialize into
fast-paths.


[^1]: For a prototypical project targeting this space, see the [Weval]()
(WebAssembly partial-evaluator) designed to provide fast AOT performance of
JavaScript.


[^2] The Lua VM contains what appears to be a switch-statement interpreter
over the current bytecode Op, with a case for each handler. The `vmswitch`,
`vmcase` and `vmbreak` macros expand into a threaded-dispatch, or computed
goto interpreter. In either case, the op-handlers are not visible symbols.
Our projection requires emitting a "must-inline" annotated function call, so
we have to refactor the interpreter loop. A second set of macros, turned on
with the `-DLUAMURA` compiler flag, makes each op-handler a visible
function.
