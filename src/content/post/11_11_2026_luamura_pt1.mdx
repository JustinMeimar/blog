> Execution of dynamically typed languages can approach native speeds with JIT
  compilation, but at what cost? 

[_Luamura_](links.luamura) is a fork of the [PUC Lua 5.5](links.lua)
interpreter that began as a weekend project to compile Lua ahead-of-time
(AOT). Implementing an AOT compiler from scratch presents a large design
space. Despite Lua being on the simpler end of the language spectrum, I
wanted to avoid re-implementation. Besides, constraints are often useful and
will help widdle down the design space for us. Therefore, the aim is to
build an AOT compiler which _reuses the Lua VM's semantics_. But before
getting into that, why even try to compile a dynamic language in the first
place?

JIT compilers map data into code at runtime. Depending on data-execution can
limit the deployment of a program to environments which (1) allow producing
code at runtime; (2) tolerate the security risks associated with JIT; and
(3) can afford a warm-up phase. A good counter-example for where these
conditions fail-to-arise is in short-lived [Function-as-a-Service
(FaaS)](links.faas) workloads running inside [WebAssembly](links.wasm)
sandboxes [^1]. Here functions often finish before a JIT could warm up, and even
if they could, WASM modules cannot directly execute data at runtime.

Now back to our design constraint: no duplication of Lua bytecode semantics.
Maintaining a single source of truth is a fundamental principle in
programming, yet JIT compilers often eschew it for pragmatic reasons
(writing backends often uses custom assembly for each tier). If a JIT has
multiple tiers, it may duplicate operator semantics in each one. V8's
Crankshaft required architecture-specific code for [nine supported
platforms](links.v8_backends) at one time. The authors of Luamura (OK, it's
just me) are frightened by the subtle and stringent intricacies of bytecode
semantics. The [first Futamura projection](links.futamura) will be the
technique we used to derive a compiled program from the existing Lua
interpreter.

## Compiling an Interpreted Language?

Whenever an interpreter is invoked with a fixed program input, why should we
not not, like a compiler, specialize the execution to that particular
program? Yes, the absence of static types can be a debilitating limitation.
However, many AOT copmilers can successfuly predict or infer types. Even
without type specialization, there is one low-hanging fruit which even
generic bytecode compilation acheives: removing dispatch overhead. For any
execution environment which isn't on-the-fly, like a web-browser,
"compiling" a traditionally interpreted language like JavaScript or Lua can
make sense [^2].

To understand what removing the dispatch overhead entails, consider a
standard bytecode interpreter. It contains a dispatch loops with handlers
for each bytecode kind. An interpreter is fully generic in that it can
execute _any_ program at-runtime. From this point, there must be an
abstraction overhead interpreters pay to achieve such generality. This is
commonly known as "dispatch overhead". Whether a [switch case
interpreter](links.switch_dispatch), or a [threaded
interpreter](links.threaded_dispatch), some amount of control flow overhead
is necessary to get from one opcode to the next.

If the bytecode is fixed we can imagine "unrolling" the interpreter loop
along allkthe paths it might take. Stamping out a copy of the handler for
each bytecode will etch out a CFG. Unlike a binary compiled from a
statically typed language, however, the blocks in our CFG will be composed
of coarse, generic VM routines rather than more-or-less direct
transliteration.

```c
// p.x in Lua: GETFIELD (inlined)
if (!ttistable(p)) luaV_finishget(...);   // not a table
slot = luaH_getshortstr(hvalue(p), "x");  // hash lookup
if (isempty(slot)) luaV_finishget(...);   // __index fallback

// p->x in C
movsd  xmm0, [rdi]
```

## The First Futamura Projection

The [Futamura projections](links.futamura) describe how partial evaluation
can derive compiled programs, compilers, and compiler generators from an
existing interpreter. The first projection specializes an interpreter to a
fixed program, and is what we pursue here in _Luamura_.

The mechanics of the FFP are slightly nebulous. Compared to
what we implement here, there are much more sophisticated implementations in
the wild. [Truffle](links.truffle) lets language implementers write
interpreters that Graal partially evaluates with respect to a fixed guest
program, producing specialized machine code. The FFP is an instance of
partial evaluation. Another project is [Weval](links.weval), which
implements the FFP as a _generic code transformation_, independent of any
particular language’s semantics. It analyzes the
interpreter-to-specialize's CFG and, given the fixed guest bytecode input,
does all of the abstract interpretation, static analysis and dataflow
required to transform the interpreter loop into the compiled program.

Compared to these techniques, Luamura is quite crude. Our only goal is to
elide the interpreter dispatch between opcodes. It is an ad-hoc FFP, which
is to say it is entirely coupled to Lua's semantics, and uses a small
compiler and runtime, plus interpreter changes (and LLVM as a dependency),
to get up and running.

## Mechanics of Luamura

The basic idea is as follows. We start by linking a small program against
`liblua`. This gives us access to the entire runtime so we don't need to
worry about garbage collection, implementing coroutines, lexing or parsing.
By passing a Lua module through the linked parsing functions we turn each
Lua function into bytecode. This is the point at which our "compiler"
starts.

For a given function, we can take the bytecode and lift it into a
[CFG](links.cfg). The branches in the CFG represent the _irreducible_
control flow of the guest program. Each basic block is still composed of
generic Lua bytecode. Therefore we need a way to compile a basic block
such that its bytecodes are executed without any dispatch
overhead between them.

If we had LLVM emit a basic block that simply called the interpreter's
handler for each op, our program would consist of a sequence of function
calls into the Lua runtime. This replaces interpreter dispatch with
function-call overhead.

```
block0:
    call luaV_OP_LOADI(A=0, sBx=1)
    call luaV_OP_LOADI(A=1, sBx=4)
    call luaV_OP_MOVE(A=2, B=0)
    call luaV_OP_RETURN1(A=2)
```

Perhaps risking an anticlimax, this seemingly pointless method of emitting
an LLVM call for each opcode handler is 99% of the way to our projection.
Consider what happens if each call is forcibly inlined. We loop over each
opcode in a basic block and emit a call to the opcode handler tagged with
the `alwaysinline` attribute. Inlining removes the calls between adjacent
handlers, while preserving their internal control flow.

```cpp
llvm::Value* BlockCompiler::compile(const CFG::Block& block) {
    llvm::Value* next = nullptr;
    for (PC pc = block.start; pc < block.end; pc++) {
        Instruction i = proto.code[pc];
        auto* call = builder.CreateCall(
            module.getOrInsertFunction(std::string("luaV_OP_") +
                                           opnames[GET_OPCODE(i)],
                                       op_handler_ty),
        call->addFnAttr(llvm::Attribute::AlwaysInline);
        next = call;
    }
    return next;
}
```

*Figure 1: Luamura's block compiler emits an always-inline opcode handler call
for each bytecode instruction. Simplified: PC setup and handler arguments
omitted ([source](links.block_compiler)).*

### Minor Implementation Challenges

There are two challenges standing in the way of this approach. First, the
Lua VMs interpreter loop uses computed-goto dispatch, meaning each opcode
handler is a label rather than a function. In a linked library these goto
labels are not visible, therefore we have no function to call and forcibly
inline.

Thankfully, the `vmswitch`, `vmcase` and `vmbreak` macros make it easy to
refactor the interpreter loop. A second set of macros, turned on with the
`-DLUAMURA` compiler flag, transforms each handler into a visible function.

```c
// default threaded-dispatch macros
#define vmdispatch(x) goto *disptab[x]
#define vmcase(op)    L_##op:
#define vmbreak       vmfetch(); vmdispatch(GET_OPCODE(i))

#if defined(LUAMURA)
// Luamura overridden macros to make each call a function
#undef vmcase
#undef vmbreak
#define vmcase(op)    CallInfo *luaV_##op()
#define vmbreak       return (*next = pc, NULL)
#endif

```

Second, even now that we can link each handler as a visible function, recall
that linking comes after compilation. Our attribute to "always inline" a
handler doesn't help much if the compiler can't see what it's inlining. To
solve this we bootstrap `lvm.c` by compiling it to LLVM bitcode, embedding
it in the compiler, and linking the definitions into each generated module.
Excluding the minor refactors to liblua, Luamura comes out to 742 lines, and
could be much shorter if code-golfed.

```git

```

This projection is effectively the simplest form of a type-generic [Baseline
Compilation](links.baseline). We trade the factored simplicity of a small
interpreter for a large binary containing every op's generic handler inlined
and duplicated repeatedly. A growth in code size can certainly be expected.

Comparing a compiled function to its interpreter counterpart, the former
effectively un-factors the de-duplicated work of the latter. While
abstracting duplicated work is the natural instinct of any programmer, for a
compiler, abstraction simply appears as indirection. CPUs like to chew
through straight-line sequences of code, so a compiler often busies itself
undoing the higher-level constructs of the language (unrolling loops,
inlining functions, devirtualizing calls, etc.) This of course has it's
limit when program sizes, and more specifically their working sets, begin
spilling out of the L1 instruction cache.

## Limitations and Future Directions

Generic opcode handlers are slow and conservative, designed to faithfully execute
any form of data (values of any type) flowing through them. Where AOT
compilers and JIT compilers for dynamic languages converge in their designs
is in a predilection for specialization. A JIT discovers specialization
opportunities through instrumenting lower tiers during warmup phases, then,
speculatively, compiling fast paths for those assumptions. An AOT compiler
shifts the source of speculation to compile time. Techniques for predicting
the types of values at a particular program point include
profiling and static type inference. For Luamura, we could pursue one or
both of these techniques to improve performance.

Code size remains a concern for any large applications. If Luamura starts generating
specialized hot paths, the generic handlers could remain out of line as
fallbacks. This effectively
boils down to the OSR-exit vs. diamond path pattern described in the [Type
Speculation article](links.speculation) from JavaScriptCore.

And before getting too excited about type-specialized hot paths, we must
recall one of the original design goals: not to duplicate Lua semantics.
The natural instinct would be to start writing custom opcode handlers in LLVM IR
which guard the assumptions they take. Even though Lua is relatively simple,
constraints are fun. I think there is a way the guarded assumptions can be
exposed as predicates on the values they encompass, and specialized fast
paths can effectively fall out by LLVM folding the generic handlers.

Other issues to address include the proliferation of stack traffic. For
example, `a + b + c` operates on tagged values in Lua VM registers, which
are stored in stack slots. To get near-native arithmetic expression performance we would need to
promote values off the stack and into native registers. This ultimately
leads down the road of modelling side effects. At any reconvergence point
between a fast path and a generic path, both paths must represent the same
observable VM state. Lua metamethods can invoke user code, complicating
assumptions about side effects.

The first thing Luamura might pursue is lifting the bytecode into [SSA](links.ssa).
From there we can consider modelling side effects, picking points to split
the code and lay out fast paths, and more. But we'll leave that for part II!


## Conclusion

Luamura achieves some marginal gains while adhering to our two constraints:
no dynamic executable memory, and reuse of interpreter semantics. This small
implementation is a good starting point, but future improvements will
require an SSA intermediate representation, some more co-design with the
interpreter, and a bunch of analysis passes to prove what VM state is safe
to specialize into fast paths.


[^1]: A prototypical compiler in this space is [Weval](links.weval)
(WebAssembly partial-evaluator) designed to provide fast AOT performance of
JavaScript. _Luamura_ being an AOT compiler avoids both the
permission-flipping of JIT compilation and its warmup.

[^2]: An interpreter receives a guest program and executes it within a
single process. If we're talking about a JavaScript engine within a browser,
the interpreter may receive a continuous sequence of scripts which it and
must attempt to execute them unconditionally. There is no compilation step,
and for a sensible reason. When the execution must occur on demand, within a
live run-time, a compilation step may not make sense. Consider if each
web-page had an additional loading phase required to compile JavaScript. Most would not be happy!
